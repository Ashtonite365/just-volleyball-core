# jv-mods rules and API spec

The rules every mod follows, and the spec of which API function links to which game feature.
Details of the API itself: [docs/API.md](docs/API.md). Gate internals: [docs/GATE.md](docs/GATE.md).

## Hard rules (always)

1. **Runtime injection only.** Nothing edits `volleyball.pck` or `volleyball.exe`; everything
   loads from `mods\` via `override.cfg` -> `res://mods/bootstrap.gd`.
2. **Version pin first.** If the game version (GameConfig.VERSION) isn't approved in `mods/pins.json`, no mod library
   loads and every API class is closed.
3. **Through the API.** A mod reaches the game only through `JVModAPI`, naming itself and
   using only the capabilities it declared in `register_mod`. Libraries not migrated yet are
   listed in docs/API.md; `mods/api.json {"strict": true}` turns them off.
4. **Fail closed.** Unknown mode, missing core, a refused call: do nothing. Revert everything
   the instant a class closes (undo calls always work for the mod's own changes).
5. **Never the game's RPCs.** Mods may observe the game's network signals; they never call its
   `@rpc` functions. Mod traffic = `jvm_*` Steam lobby keys and JVMS packets to peers that said
   HELLO (unmodded players get nothing).
6. **Original assets only.** No ripped or copied art; shared packs are data (PNG/JSON/glb),
   never code (`allow_scripts` stays off for shared content).
7. **Keep the user's configs** (goofy, shots, picker.json, equipped.json, model_settings.json,
   user packs) across updates.

## Gate rules per access class

| access class | Free Play / practice / offline solo | main menu | LAN | private lobby | friends-only lobby | public lobby / quick match / server browser | unknown |
|---|---|---|---|---|---|---|---|
| `read` | yes | yes | yes | yes | yes | yes | yes |
| `local_ui` | yes | yes | yes | yes | yes | yes | yes |
| `cosmetic` | yes | yes (local) | yes | yes | yes | **local only** | no |
| `gameplay` | yes | yes | yes | yes | yes | no | no |
| `sync` | no (nobody to sync with) | no | yes | yes | yes | no | no |
| `offline` | yes | yes | no | no | no | no | no |

In words: **Free Play / offline: everything. LAN, private and friends-only: the full set,
including sync. Public: local only** (our own looks on our own screen, nothing that changes
play or talks to anyone). Nothing is open until the version pin matched, and `read` /
`local_ui` never change the game. `tests/test_api.cpp` checks this whole matrix.

Where the mode comes from: docs/GATE.md (Net.active / custom_lobby / privacy / party_lan,
GameConfig.quick_match / net_roster, the menu's practice and Free Play flags).

`engine.time_scale` is `gameplay` today (unchanged behaviour). It is not synced, so it is the
first candidate to move to `offline` (the project owner's call).

## Scope

* `local` - changes only this PC.
* `host` - only the host's value counts; it reaches everyone through the game's own sync
  (e.g. touch counts in player state). Clients display, the host enforces.
* `peers` - data we send to modded peers ourselves; needs `sync`.

## Adding or changing a capability

1. Add a `JV_CAP(...)` line to `src/api/capabilities.def` with game refs written as `path:? symbol`.
2. `tools/check_api_refs.py --fix` fills in the lines; `tools/gen_api_docs.py` refreshes the tables here and in docs/API.md.
3. Implement the functions in `src/core/mod_api.cpp` (status `IMPL`), test them in
   `tests/fakegame/api_tests.gd`, bump the API minor version.
4. After a game update: `tools/gen_game_surface.py > docs/GAME_SURFACE.md`, then
   `tools/check_api_refs.py` and fix what moved (patch version).
